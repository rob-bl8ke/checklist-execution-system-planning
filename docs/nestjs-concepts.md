# NestJS Concepts — Learning Guide from the Codebase

Concepts ordered from beginner → expert. Every entry is backed by real code in `checklist-execution-system-api/src/`.

> **How to use this table:** Open the file(s) listed in the **Where to Look** column side-by-side with the NestJS docs link. Each row is a self-contained learning unit.

## Level 1 — Foundations (start here)

| # | Concept | What It Is | What the Codebase Showcases | Where to Look | Technique / Docs to Search | Angular / UI Parallel |
|---|---------|------------|-----------------------------|---------------|----------------------------|----------------------|
| 1 | **Bootstrap & Entry Point** | `NestFactory.create()` spins up the app, similar to `platformBrowserDynamic().bootstrapModule()` in Angular. The `bootstrap()` function is the single startup script. | Creates the app from `AppModule`, sets global prefix `api`, registers global pipes, enables CORS, configures Swagger, then listens on a port. | `main.ts` | [NestJS First Steps](https://docs.nestjs.com/first-steps) | Angular's `main.ts` calling `bootstrapApplication()` |
| 2 | **Modules (`@Module`)** | The organizational unit of a Nest app. Groups related controllers, providers, and imports. Exactly like Angular's `@NgModule` (or standalone component `imports`). | `AppModule` is the root; feature modules (`TemplatesModule`, `TodoModule`, `InstanceModule`, `DashboardModule`) each own one entity domain. | `app.module.ts`, `template/template.module.ts`, `todo/todo.module.ts`, `instance/instance.module.ts`, `dashboard/dashboard.module.ts` | [NestJS Modules](https://docs.nestjs.com/modules) | Angular `@NgModule` / standalone component `imports` array |
| 3 | **Controllers (`@Controller`)** | Handle incoming HTTP requests and return responses. Decorated with route prefixes. Like Angular components that "own" a route, but for the server side. | `TemplatesController` handles `/templates`, `TodosController` handles `/todos`, `DashboardController` handles `/dashboard`. Each delegates to a service. | `template/templates.controller.ts`, `todo/todos.controller.ts`, `dashboard/dashboard.controller.ts` | [NestJS Controllers](https://docs.nestjs.com/controllers) | Angular route components — each "page" has a component, here each URL path has a controller |
| 4 | **Providers & Services (`@Injectable`)** | Classes marked `@Injectable()` that contain business logic. Registered as `providers` in a module. Nest's DI container manages them as singletons by default. | `TemplatesService`, `TodosService`, `InstancesService`, `DashboardService`, `VariableExtractionService` — all decorated with `@Injectable()` and injected via constructors. | `template/templates.service.ts`, `todo/todos.service.ts`, `app.service.ts` | [NestJS Providers](https://docs.nestjs.com/providers) | Angular services with `@Injectable({ providedIn: 'root' })` |
| 5 | **Dependency Injection (constructor injection)** | Nest resolves dependencies automatically by type when declared in the constructor. This is the exact same DI pattern Angular uses. | Every controller receives its service via `constructor(private readonly templatesService: TemplatesService)`. Services receive repositories the same way. | `template/templates.controller.ts` (line 22), `todo/todos.controller.ts` (line 20) | [NestJS Custom Providers](https://docs.nestjs.com/fundamentals/custom-providers) | Angular constructor-based DI: `constructor(private http: HttpClient)` |
| 6 | **Decorators** | TypeScript decorators (`@`) attach metadata to classes, methods, and parameters. Nest is built entirely on decorators, just like Angular. | `@Module`, `@Controller`, `@Injectable`, `@Get`, `@Post`, `@Body`, `@Param`, `@Column`, `@Entity` — used everywhere. | Every file in the project | [TypeScript Decorators](https://www.typescriptlang.org/docs/handbook/decorators.html) | Angular uses `@Component`, `@Input`, `@Output`, `@Inject` in the same way |

## Level 2 — Routing & Request Handling

| # | Concept | What It Is | What the Codebase Showcases | Where to Look | Technique / Docs to Search | Angular / UI Parallel |
|---|---------|------------|-----------------------------|---------------|----------------------------|----------------------|
| 7 | **Route Decorators (`@Get`, `@Post`, `@Put`, `@Patch`, `@Delete`)** | Map controller methods to HTTP verbs. The method return value becomes the JSON response body. | Full CRUD: `@Get()` list, `@Get(':id')` find one, `@Post()` create, `@Put(':id')` update, `@Delete(':id')` remove, `@Patch(':id')` partial update. | `template/templates.controller.ts`, `todo/todos.controller.ts`, `instance/instances.controller.ts` | [NestJS Routing](https://docs.nestjs.com/controllers#routing) | No direct Angular parallel — Angular routing maps URLs to components, not HTTP verbs |
| 8 | **Route Parameters (`@Param`)** | Extract dynamic URL segments. `@Param('id')` pulls the `:id` from `/templates/:id`. | Every `findOne`, `update`, `remove` method uses `@Param('id', ParseIntPipe) id: number`. Nested routes use `@Param('templateId')` and `@Param('stepId')`. | `template/templates.controller.ts`, `template-step/template-steps.controller.ts` | [NestJS Route Parameters](https://docs.nestjs.com/controllers#route-parameters) | Angular `ActivatedRoute.params` or `input()` from route params |
| 9 | **Request Body (`@Body`)** | Extract and bind the JSON request body to a DTO class. Validation runs automatically when a `ValidationPipe` is active. | Every `create` and `update` method: `@Body() dto: CreateTemplateDto`. | `template/templates.controller.ts`, `instance/instances.controller.ts` | [NestJS Request object](https://docs.nestjs.com/controllers#request-object) | Angular reactive forms — `FormGroup` validates input client-side, `@Body` + DTO validates server-side |
| 10 | **Nested / Sub-Resource Routes** | Controllers can use path prefixes with multiple parameters for parent-child relationships. | `@Controller('templates/:templateId/steps')` — all template-step routes are nested under a template. `@Patch(':instanceId/steps/:stepId')` for instance step completion. | `template-step/template-steps.controller.ts`, `instance/instances.controller.ts` | [NestJS Sub-Domain Routing](https://docs.nestjs.com/controllers#sub-domain-routing) | Angular child routes: `{ path: 'templates/:id', children: [...] }` |
| 11 | **HTTP Status Codes (`@HttpCode`)** | Override the default status code (200 for GET, 201 for POST). | `@HttpCode(HttpStatus.CREATED)` on POST endpoints, `@HttpCode(HttpStatus.NO_CONTENT)` on DELETE endpoints. | `template/templates.controller.ts` (POST, DELETE), `todo/todos.controller.ts` (DELETE) | [NestJS Status Code](https://docs.nestjs.com/controllers#status-code) | No direct parallel — HTTP status codes are a server concept |
| 12 | **Built-in Pipes (`ParseIntPipe`)** | Transform and validate route/query parameters before they reach the handler. `ParseIntPipe` converts string `:id` to a number and returns 400 if invalid. | Used on every `:id` parameter in every controller: `@Param('id', ParseIntPipe) id: number`. | `template/templates.controller.ts`, `instance/instances.controller.ts` | [NestJS Pipes](https://docs.nestjs.com/pipes) | Angular `| number` Pipe in templates — transforms display values; Nest pipes transform input values |
| 13 | **Global Prefix** | `app.setGlobalPrefix('api')` prepends `/api` to every route, so `@Controller('templates')` actually serves `/api/templates`. | Set in `main.ts` — all routes have `/api/` prefix. | `main.ts` (line 9) | [NestJS Global Prefix](https://docs.nestjs.com/faq/global-prefix) | Angular `APP_BASE_HREF` or `<base href="/">` |

## Level 3 — Validation & DTOs

| # | Concept | What It Is | What the Codebase Showcases | Where to Look | Technique / Docs to Search | Angular / UI Parallel |
|---|---------|------------|-----------------------------|---------------|----------------------------|----------------------|
| 14 | **DTOs (Data Transfer Objects)** | Plain classes that define the shape of incoming request data. Not interfaces — they're classes so decorators can attach validation metadata at runtime. | Separate Create/Update DTOs for each entity: `CreateTemplateDto`, `UpdateTemplateDto`, `CreateTodoDto`, `UpdateTodoDto`, `CreateInstanceDto`, `CompleteStepDto`, `UpdateInstanceStatusDto`, `MoveTemplateStepDto`. | `template/dto/`, `todo/dto/`, `instance/dto/`, `template-step/dto/` | [NestJS Validation](https://docs.nestjs.com/techniques/validation) | Angular interfaces/models in `api.models.ts` — but Nest uses classes so validation decorators work |
| 15 | **`class-validator` Decorators** | Library that provides validation decorators: `@IsString()`, `@IsNotEmpty()`, `@IsOptional()`, `@IsBoolean()`, `@IsEnum()`, `@IsPositive()`, `@MaxLength()`, `@IsInt()`, `@IsObject()`. | Used in every DTO. Examples: `@IsString() @IsNotEmpty() name`, `@IsPositive() templateId`, `@IsEnum(InstanceStatus) status`, `@MaxLength(10) variablePrefix`. | `template/dto/create-template.dto.ts`, `instance/dto/create-instance.dto.ts`, `todo/dto/update-todo.dto.ts` | [class-validator GitHub](https://github.com/typestack/class-validator) | Angular `Validators.required`, `Validators.maxLength()` in reactive forms — same concept, different layer |
| 16 | **`ValidationPipe` (global)** | Automatically validates every incoming request body against the DTO's decorators. `whitelist: true` strips unknown properties; `forbidNonWhitelisted: true` rejects them with 400. | Configured globally in `main.ts`: `app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true }))`. | `main.ts` (lines 11-13) | [NestJS ValidationPipe](https://docs.nestjs.com/techniques/validation#using-the-built-in-validationpipe) | No Angular parallel — this is server-side input sanitization (OWASP: Mass Assignment prevention) |
| 17 | **Custom Validator (`registerDecorator`)** | Create domain-specific validation rules as reusable decorators by calling `registerDecorator()` from `class-validator`. | `@BothOrNeither('variableSuffix')` ensures `variablePrefix` and `variableSuffix` are either both provided or both absent. Implements cross-field validation. | `common/both-or-neither.validator.ts`, used in `template/dto/create-template.dto.ts` | [class-validator Custom Decorators](https://github.com/typestack/class-validator#custom-validation-decorators) | Angular cross-field validators on `FormGroup` — same idea of "validate two fields together" |
| 18 | **Optional vs Required Fields** | Create DTOs have required fields; Update DTOs mark everything `@IsOptional()` so partial updates work. This is a manual pattern (some projects use `PartialType()` from `@nestjs/mapped-types`). | Compare `CreateTemplateDto` (name required) with `UpdateTemplateDto` (name is `@IsOptional()`). Same for `CreateTodoDto` vs `UpdateTodoDto`. | `template/dto/create-template.dto.ts` vs `template/dto/update-template.dto.ts` | [NestJS Mapped Types](https://docs.nestjs.com/openapi/mapped-types) | Angular optional form fields — `FormControl` with/without `Validators.required` |

## Level 4 — Database & ORM (TypeORM)

| # | Concept | What It Is | What the Codebase Showcases | Where to Look | Technique / Docs to Search | Angular / UI Parallel |
|---|---------|------------|-----------------------------|---------------|----------------------------|----------------------|
| 19 | **TypeORM Entities (`@Entity`)** | Classes that map to database tables. Column decorators define the schema. This is the ORM layer — the single source of truth for your database schema. | `Template`, `TemplateStep`, `Instance`, `InstanceStep`, `Todo` — each maps to a table with `@PrimaryGeneratedColumn`, `@Column`, `@CreateDateColumn`, `@UpdateDateColumn`. | `template/template.entity.ts`, `todo/todo.entity.ts`, `instance/instance.entity.ts`, `instance/instance-step.entity.ts`, `template-step/template-step.entity.ts` | [TypeORM Entity docs](https://typeorm.io/entities) | No direct parallel — Angular doesn't have an ORM; closest is TypeScript interfaces for API response shapes |
| 20 | **Column Types & Options** | `@Column({ type: 'text', nullable: true, name: 'snake_case' })` maps a camelCase TS property to a snake_case DB column with specific type and constraints. | `variable_prefix` / `variablePrefix` naming, `type: 'real'` for fractional positions, `type: 'text'` for strings, `default` values, `nullable`. | `template/template.entity.ts`, `template-step/template-step.entity.ts`, `instance/instance.entity.ts` | [TypeORM Column Types](https://typeorm.io/entities#column-types) | — |
| 21 | **Column Transformers** | TypeORM `transformer: { to, from }` lets you serialize/deserialize values between JS and the database — e.g., storing a JS object as JSON text in SQLite. | `Instance.variables` uses a transformer to `JSON.stringify` on write and `JSON.parse` on read, storing a `Record<string, string>` as TEXT. | `instance/instance.entity.ts` (lines 24-33) | [TypeORM Column Transformer](https://typeorm.io/entities#column-options) | — |
| 22 | **Entity Relationships (`@OneToMany`, `@ManyToOne`)** | Decorators that define foreign-key relationships between entities. `@OneToMany` is the "one" side, `@ManyToOne` is the "many" side with the FK column. | `Template` → `TemplateStep` (one-to-many with `cascade: true`). `TemplateStep` → `Template` (many-to-one with `onDelete: 'CASCADE'`). Same pattern for `Instance` → `InstanceStep`. | `template/template.entity.ts`, `template-step/template-step.entity.ts`, `instance/instance.entity.ts` | [TypeORM Relations](https://typeorm.io/relations) | — |
| 23 | **Cascade & `onDelete`** | `cascade: true` on `@OneToMany` means saving a parent auto-saves children. `onDelete: 'CASCADE'` on `@ManyToOne` means deleting a parent deletes children at the DB level. | Template deletion cascades to template steps. Instance deletion cascades to instance steps. | `template/template.entity.ts` (`cascade: true`), `template-step/template-step.entity.ts` (`onDelete: 'CASCADE'`) | [TypeORM Cascades](https://typeorm.io/relations#cascades) | — |
| 24 | **`TypeOrmModule.forRoot()` & `.forFeature()`** | `forRoot()` configures the DB connection once in `AppModule`. `forFeature([Entity])` registers repositories for specific entities in feature modules. Exactly like Angular's `forRoot`/`forChild` pattern on `RouterModule`. | Root config in `app.module.ts` with `better-sqlite3`. Feature modules use `forFeature`: `TemplatesModule` registers `[Template]`, `InstanceModule` registers `[Instance, InstanceStep, Template]`. | `app.module.ts` (forRoot), `template/template.module.ts` (forFeature), `instance/instance.module.ts` (forFeature) | [NestJS TypeORM Integration](https://docs.nestjs.com/techniques/database) | Angular `RouterModule.forRoot()` vs `RouterModule.forChild()` — same "configure once, register features" pattern |
| 25 | **Repository Pattern (`@InjectRepository`)** | `@InjectRepository(Entity)` injects a TypeORM `Repository<Entity>` — a generic data-access object with `find`, `findOne`, `save`, `remove`, `create`, `createQueryBuilder`. | Every service injects one or more repositories. `TemplatesService` injects `Repository<Template>`, `InstancesService` injects three separate repositories. | `template/templates.service.ts`, `todo/todos.service.ts`, `instance/instances.service.ts` | [NestJS Repository Pattern](https://docs.nestjs.com/techniques/database#repository-pattern) | Angular's `HttpClient` is the data-access layer equivalent — both abstract away raw data operations |
| 26 | **Query Builder** | `repo.createQueryBuilder()` lets you write type-safe SQL-like queries for complex reads (joins, aggregates, raw selects). | `TemplatesService.findAll()` uses QueryBuilder with `leftJoin`, `select`, `addSelect`, `groupBy`, `getRawMany` to get step counts. `DashboardService` uses an inner join to fetch next steps efficiently. | `template/templates.service.ts` (findAll), `dashboard/dashboard.service.ts` (getToday) | [TypeORM QueryBuilder](https://typeorm.io/select-query-builder) | — |
| 27 | **Migrations** | Version-controlled SQL scripts that evolve the database schema. Generated from entity changes. Reversible with `up()` / `down()` methods. | Two migrations in `database/migrations/`. `CreateTodo` creates all initial tables with FK constraints. `AddVariableDelimiters` adds columns to an existing table. Scripts: `migration:generate`, `migration:run`, `migration:revert`. | `database/migrations/`, `database/data-source.ts`, `migrate.ts`, `package.json` (scripts) | [TypeORM Migrations](https://typeorm.io/migrations) | No Angular parallel — migrations are a backend/DB concern |
| 28 | **DataSource (standalone)** | A separate `DataSource` config used by the TypeORM CLI for generating and running migrations outside the Nest app lifecycle. | `database/data-source.ts` exports `AppDataSource` with entity/migration glob paths. `migrate.ts` initializes it and runs migrations programmatically. | `database/data-source.ts`, `migrate.ts` | [TypeORM DataSource](https://typeorm.io/data-source) | — |

## Level 5 — Error Handling & HTTP Exceptions

| # | Concept | What It Is | What the Codebase Showcases | Where to Look | Technique / Docs to Search | Angular / UI Parallel |
|---|---------|------------|-----------------------------|---------------|----------------------------|----------------------|
| 29 | **Built-in HTTP Exceptions** | Nest provides exception classes (`NotFoundException`, `BadRequestException`, `ConflictException`) that automatically set the HTTP status code and error response body. | `NotFoundException` thrown in every `findOne`/`update`/`remove` when entity not found (404). `BadRequestException` for invalid move operations. `ConflictException` when toggling steps on an ABANDONED instance. | `template/templates.service.ts` (NotFoundException), `template-step/template-steps.service.ts` (BadRequestException), `instance/instances.service.ts` (ConflictException) | [NestJS Exception Filters](https://docs.nestjs.com/exception-filters) | Angular `HttpErrorResponse` — catches these on the client side; Nest throws them on the server side |
| 30 | **Exception-driven flow control** | Rather than returning error codes, services throw exceptions and Nest's built-in exception filter converts them to the correct HTTP response. This is a pattern, not just a feature. | Services never return `null` or error objects. They `throw new NotFoundException(...)` and the framework handles the rest. Controllers don't need try/catch. | `template/templates.service.ts` (findOne), `todo/todos.service.ts` (update/remove) | [NestJS Exception Filters](https://docs.nestjs.com/exception-filters) | Similar to Angular's `ErrorHandler` or HTTP interceptors that catch errors globally |

## Level 6 — Module Architecture Patterns

| # | Concept | What It Is | What the Codebase Showcases | Where to Look | Technique / Docs to Search | Angular / UI Parallel |
|---|---------|------------|-----------------------------|---------------|----------------------------|----------------------|
| 31 | **Feature Module Pattern** | Each domain (template, instance, todo, dashboard) is a self-contained module with its own controller, service, and entity. This is the recommended Nest architecture. | 5 feature modules: `TemplatesModule`, `TemplateStepModule`, `InstanceModule`, `TodoModule`, `DashboardModule`. Each imports only the TypeORM features it needs. | All `*.module.ts` files | [NestJS Modules](https://docs.nestjs.com/modules) | Angular feature modules / lazy-loaded route modules |
| 32 | **Module `exports`** | Making a provider available to other modules that import this module. Without `exports`, a service is private to its own module. | `TemplatesModule` exports `TemplatesService`. `TodoModule` exports `TodosService`. `InstanceModule` exports `InstancesService` and `VariableExtractionService`. | `template/template.module.ts`, `todo/todo.module.ts`, `instance/instance.module.ts` | [NestJS Shared Modules](https://docs.nestjs.com/modules#shared-modules) | Angular `exports` array on `@NgModule` — same concept of making things public |
| 33 | **Cross-Module Repository Access** | A module can import entities from other domains via `TypeOrmModule.forFeature()` to access their repositories directly, without importing the entire module. | `InstanceModule` imports `[Instance, InstanceStep, Template]` — it needs the `Template` repo directly. `DashboardModule` imports `[Instance, InstanceStep, Todo]` — aggregates across domains. `TemplateStepModule` imports `[TemplateStep, Template]` to validate parent existence. | `instance/instance.module.ts`, `dashboard/dashboard.module.ts`, `template-step/template-step.module.ts` | [NestJS TypeORM forFeature](https://docs.nestjs.com/techniques/database#repository-pattern) | Angular components importing shared services from other modules |

| 36 | **Unit Tests with `TestBed` (`Test.createTestingModule`)** | Nest's `Test.createTestingModule()` creates an isolated DI container for testing — exactly like Angular's `TestBed.configureTestingModule()`. | Every `.spec.ts` file creates a testing module with mock providers. ## Level 9 — Advanced Patterns

| # | Concept | What It Is | What the Codebase Showcases | Where to Look | Technique / Docs to Search | Angular / UI Parallel |
|---|---------|------------|-----------------------------|---------------|----------------------------|----------------------|
| 41 | **Transactions (`DataSource.createQueryRunner`)** | Wrap multiple database operations in an atomic transaction. If any step fails, all changes roll back. Uses the QueryRunner pattern from TypeORM. | `InstancesService.create()` — inside a transaction: creates instance, creates all instance steps from template, then sets `nextStepId`. Uses `try/catch/finally` with `commit`, `rollback`, `release`. | `instance/instances.service.ts` (create method, lines 60-115) | [TypeORM Transactions](https://typeorm.io/transactions), [NestJS Transactions](https://docs.nestjs.com/techniques/database#transactions) | No direct Angular parallel — transactions are a backend data-integrity concept |
| 42 | **Service-Layer Composition** | One service can orchestrate work across multiple repositories it injects, keeping controllers thin. | `InstancesService` injects `Instance`, `InstanceStep`, AND `Template` repos — it reads the template to copy steps into a new instance. `DashboardService` aggregates data from `Instance`, `InstanceStep`, and `Todo` repos. | `instance/instances.service.ts`, `dashboard/dashboard.service.ts` | — | Angular services injecting other services — same composition pattern |
| 43 | **Derived / Computed Response Fields** | Add fields to API responses that don't exist in the database — computed at query time in the service layer. | `TemplatesService.findAll()` returns `stepCount` (computed via SQL COUNT). `InstancesService.findAll()` returns `nextStep` and `progress` (computed from step data). | `template/templates.service.ts` (findAll), `instance/instances.service.ts` (toSummary) | — | Angular computed signals — derived state that's calculated from source data |
| 44 | **Gap-Based Ordering (Rebalance Algorithm)** | A positional ordering system where items have gaps (100, 200, 300) allowing insertion by midpoint. When gaps get too small (< 1), a rebalance reassigns all positions. | `TemplateStepsService.move()` implements the full algorithm: midpoint insertion, first/last positioning, and automatic rebalance when gap < 1. | `template-step/template-steps.service.ts` (move & rebalance methods), `template-step/template-step.entity.ts` (JSDoc comment) | Search: "fractional indexing", "gap-based ordering" | — |
| 45 | **State Machine Logic in Services** | Business rules for valid state transitions, enforced in the service layer. | `InstancesService.completeStep()`: auto-transitions to COMPLETED when all steps done, reverts to IN_PROGRESS when un-completing, blocks toggling on ABANDONED instances (throws `ConflictException`). `updateStatus()` enforces allowed transitions. | `instance/instances.service.ts` (completeStep, updateStatus) | Search: "state machine pattern in services" | Angular state management with signals/NgRx — tracking valid state transitions |
| 46 | **Template Variable Rendering** | A pipeline that finds placeholder variables in strings, resolves them from a variable map, and applies chained transforms. | `renderInstructions()` uses regex with configurable delimiters to find `{{varName}}`, resolves the value, and applies transforms via `evaluate()`. The transform pipeline supports piped operations: `{{name \| upper \| truncate(10)}}`. | `instance/instances.service.ts` (renderInstructions), `instance/transform-pipeline.ts`, `instance/transform-registry.ts` | Search: "template engine", "pipe transform chain" | Angular pipes: `{{ value \| uppercase \| slice:0:10 }}` — almost identical syntax and concept! |
| 47 | **Registry Pattern (Transform Registry)** | A `Map<string, Function>` lookup table for named operations. Decouples the pipeline from individual transform implementations. New transforms are added by inserting into the map. | `transform-registry.ts` exports a Map of 15 named transforms: `upper`, `lower`, `capitalize`, `snake_case`, `kebab_case`, `replace`, `default`, `truncate`, `pad_left`, etc. | `instance/transform-registry.ts` | Search: "function registry pattern", "strategy pattern" | Angular's `Pipe` registry — each pipe is a named transform function |
| 48 | **Utility Service vs Pure Function** | `@Injectable()` services for logic needing DI; plain exported functions for pure, dependency-free logic. | `VariableExtractionService` is `@Injectable()` because it might need DI in the future. `escapeRegex()`, `evaluate()`, `getTransform()` are pure functions — no DI needed, directly importable, easily testable. | `instance/variable-extraction.service.ts` (Injectable), `common/escape-regex.ts` (pure fn), `instance/transform-pipeline.ts` (pure fn) | [NestJS Custom Providers](https://docs.nestjs.com/fundamentals/custom-providers) | Angular standalone functions vs Injectable services — same design decision |
| 49 | **CORS Configuration** | `app.enableCors()` allows the Angular frontend (different origin) to call the API. Without this, browser security blocks cross-origin requests. | Single line in `main.ts`: `app.enableCors()`. Currently allows all origins (suitable for development). | `main.ts` (line 15) | [NestJS CORS](https://docs.nestjs.com/security/cors) | Angular's `HttpClient` is the consumer of this — CORS errors appear in the browser console when this isn't configured |
| 50 | **Environment-Based Configuration** | Using `process.env` with fallback defaults for runtime configuration like database path and port. | `process.env.DB_PATH ?? 'checklist.db'` and `process.env.PORT ?? 3000`. `database/data-source.ts` uses `__filename.endsWith('.js')` to detect compiled vs source mode for entity/migration paths. | `app.module.ts`, `main.ts`, `database/data-source.ts` | [NestJS Configuration](https://docs.nestjs.com/techniques/configuration) | Angular `environment.ts` / `environment.development.ts` — same concept of per-environment config |

## Concept Map — How It All Connects

```
main.ts (bootstrap)
  └─ AppModule (@Module - root)
       ├─ TypeOrmModule.forRoot()          ← DB connection config
       ├─ TemplatesModule                  ← Feature module
       │    ├─ TypeOrmModule.forFeature()  ← Register entity repos
       │    ├─ TemplatesController         ← HTTP routes (@Get, @Post...)
       │    │    └─ @Body() dto            ← Validated by ValidationPipe
       │    └─ TemplatesService            ← Business logic (@Injectable)
       │         └─ @InjectRepository()    ← TypeORM Repository<T>
       ├─ InstanceModule
       │    └─ InstancesService
       │         ├─ DataSource             ← Transactions
       │         └─ transform-pipeline.ts  ← Pure utility (no DI)
       ├─ TodoModule
       ├─ DashboardModule                  ← Aggregates across modules
       └─ AppController / AppService       ← Root health-check route
```

## Recommended Learning Path

1. **Start** with `todo/` — it's the simplest CRUD module (entity → service → controller → DTO → spec)
2. **Then** `template/` — adds relationships, query builder, step counts
3. **Then** `template-step/` — nested routes, gap ordering, move/rebalance algorithm
4. **Then** `instance/` — transactions, variable rendering, state machines, multi-repo injection
5. **Then** `dashboard/` — cross-module aggregation, complex queries
6. **Finally** `main.ts` + `app.module.ts` — the bootstrap and root wiring
